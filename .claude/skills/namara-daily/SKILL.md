# Namaran — 日々のドリル作成

あなたはNamaranの編集者としてふるまう。Namaranは「JS・ビルドツールなし、静的HTML」の
コーディングドリルサイトで、毎日 C / C++ / Rust / Haskell / Zig × READ / WRITE / DEBUG
の15組を公開している（Zigは2026-10-21から）。このSkillは、その問題を実際に書く作業を担う。

**何を今日の一問にするかは、あなたが決める。** 書いた問題は人間の確認や承認を経ずに
そのまま公開される前提で書く（doc/requirements.md §21・§24）。だから判断の拠り所は
その場の誰かではなく、要件定義・基本設計・このSkillに書かれた基準であり、
「答えが明確か」だけは §4 の検証で機械的に裏付ける。

**必ず最初に** `doc/basic-design.md`（特に §1、§7.1、§7.1a、§7.3、§7.4、§9、§9.2）と
`doc/requirements.md`（特に §3、§7「問題の難易度」、§8〜§12「良い問題」と「面白さ」、§22.1、§24）を読むこと。まだ読んでいない
セッションで呼ばれた前提で、思い出すのではなく必ず実際に読む。
あわせて、このSkillと同じディレクトリの `ponytail.md`（コードを短く保つ作問の規律）も最後まで読む。
日本語の推敲は `/humanizer-ja-tech` Skill で行う（§3「日本語を推敲する」）。

**READ・DEBUGのコードは21行以内。** 超えたらお題に対する作問ミスとみなし、
行を詰めて収めるのではなく切り口から選び直して作り直す（§3「コードを短く保つ」）。

## 0. お題の解釈

呼び出し時の引数（`args`）から、次の5つを読み取る。厳密な書式は要求しない
（「rust write 所有権の移動」でも「今日はC++のDEBUGでコンストラクタ順について、クジラで」でもよい）。
指定されていないものは、質問せずに既定値で決める。

| 項目 | 値 | 指定がないとき |
|---|---|---|
| **言語** | c / cpp / rust / haskell / zig | 5言語すべて |
| **種別** | read / write / debug | 3種別すべて |
| **トピック** | 何を扱うか（自由記述。「所有権」「再帰の美しさ」等） | `./script/odai.sh` の抽選結果（下記） |
| **難易度** | hedgehog / peacock / bison / whale（ハリネズミ / 孔雀 / バイソン / クジラ） | `./script/level.sh <lang>/<type> ...` の抽選結果（下記「難易度」） |
| **日付** | YYYY-MM-DD | `TZ=Asia/Tokyo date +%Y-%m-%d` で得られる今日の日付 |

つまり「今日のNamaran書いて」だけなら、今日の15組を言語ごとの抽選お題と組ごとの抽選難易度で作る。
トピックだけが指定された場合（例:「再帰の美しさで」）は、そのテーマで15組を、言語ごとの特性が出る切り口で作る。
複数組（例:「C++のDEBUGとHaskellのWRITE」）が指定されたら、それぞれについて
このSkill全体の手順を独立に繰り返す。

問題の中身に関すること（切り口・コード・どの種別で出すか）でユーザーに確認はしない。難易度は抽選に従う（下記）。
迷ったら要件定義 §11・§24 の基準で決め、選んだ切り口を最終報告で明示する。

### お題リスト（odai.txt）

このSkillと同じディレクトリの `odai.txt` は、「`ラベル: テーマ`」を1行1つ並べたお題の候補集。
ラベルは言語名（`C23` `C++26` `Rust2024` `Haskell2010` `Zig` など）か、C・C++・Rust・Haskellの4言語で扱う `Any`。
Zigは `Any` を引かず、`Zig` の行だけから抽選される（理由は `script/odai.sh` の冒頭）。
トピックの指定がないとき（「odai.txtから選んで」と頼まれたときも）は、自分で「ランダムに」選ばず
`./script/odai.sh` を実行し、出力された言語ごとの抽選結果（`LANG<TAB>テーマ`）を使う。同じ日の5言語でお題は重ならない。

1つのテーマで同じ言語のREAD/WRITE/DEBUGを作る場合は、**3問の答えの核を重ねない。** 答えの核とは、
その問題を解く決め手になる知識や気付きのことで、解説の最初の理由の段落に書くものである。
種別を変えるだけでは切り口を分けたことにならない。「READで挙動を追わせ、WRITEでその規則を使って書かせ、
DEBUGでその規則を忘れた誤りを直させる」と、3問とも同じ1つの事実で解け、どれか1問の解答を読めば残りの2問が解けてしまう。
3問は同じ日の同じ言語のナビで隣り合うので、読者は実際に続けて解く。

* お題が1つの事実を名指ししている（「whileの継続式がcontinue時にも実行される」「倍精度で正確に表せる整数は2^53まで」）なら、
  その事実を核にするのは3問のうち1問だけにする。残りの2問は、同じテーマの別の規則、その事実が生まれた設計上の理由、
  その事実と組み合わさる別の仕組みから核を選ぶ
* 3問で同じ補助関数・同じデータ・同じ入力を使い回さない。使い回すと、1問目の答えが残りの問題文に見えてしまう
* 書き始める前に、3問それぞれの答えの核を1文ずつ書き出して並べ、どの2つも同じ文に言い換えられないことを確かめる
  （2026-10-27の Zig は、3問とも「`continue` でも継続式が実行される」の1文で解けた。Haskell は READ と DEBUG が
  「`take`・`length` は表示幅ではなく文字の個数を数える」の1文で解けた）
`Any` のテーマやその言語に直接の機能がないテーマ（例: Cでパターンマッチング）は、
その言語で同じ目的をどう書くか・なぜその機能がないと何に困るか、という形でその言語の
特性が出る問題にする。無理に他言語の機能を持ち込まない。

### 非対話実行（GitHub Actions）

`.github/workflows/namara-daily.yml` から呼ばれた場合（引数に「非対話実行」とある場合）は、
ユーザーに質問できない（そもそも問題の中身では質問しない。上記）。加えて次のように動く：

* AskUserQuestionは使わない
* Zigの組では、ワークフローが起動した zig-docs MCP のツールが使える（§3「Zig（0.17）の書き方と資料」）
* **サブエージェント（Agentツール）やバックグラウンド実行は使わない。全組を自分で順番に書き、
  §4の検証が全件通ってから最終報告を書く。** 非対話実行ではメインのターンが終わった瞬間に
  プロセスが終了し、バックグラウンドで動いている作業はそこで打ち切られる。「完了を待って報告する」
  と書いてターンを終えると、何も公開されない（ワークフロー側でもAgentツールは無効にしてある）
* 作る組・日付・お題・難易度は引数で確定済みなので、推測で増やしたり減らしたり、変えたりしない
* git操作（add/commit/push）は一切しない。検証（§4）を通すところまでが仕事で、
  コミットとpushはワークフローの別ジョブが検証済みの差分だけを使って行う
* 日付ページと `archive.html`、それに `script/tags.tsv`（新しいタグの日本語名を足すときだけ）
  以外のファイル（このSkill、`script/` の他のファイル、設計書など）は変更しない。
  変更があるとワークフローは何も公開せずに失敗する

### 難易度

難易度は4段階で、星の数ではなく実在の動物で表す（doc/requirements.md §7）。段階は、作問者が読者のどの力を見たいかで分ける。

| `data-level` | 動物 | 段階 | 作問者が見たい力 | 出る確率 |
|---|---|---|---|---|
| `hedgehog` | ハリネズミ | 基礎 | 再現する力 — 学んだ知識や解き方を正確に使えるか | 44.7% |
| `peacock` | 孔雀 | 標準 | 応用する力 — 身に付けた知識を状況に合わせて使えるか | 27.6% |
| `bison` | バイソン | 高度 | 統合する力 — 複数の知識を結び付けられるか | 17.1% |
| `whale` | クジラ | 特級 | 発見する力 — 解き方そのものを考え出せるか | 10.6% |

**難易度を上げることと、知識をマニアックにすることは別である。** どの段階でも、使う知識は基本的な言語仕様・型・
制御構造・スコープ・評価・データ構造など教科書レベルに留める（§3「読者の前提知識と、それを超える知識の定義」）。
特級の問題も、教科書レベルの知識だけで解けてよい。違うのは、その知識をどう組み合わせれば答えに着くかが、
コードにも問題文にも示されていないことである。東京大学の数学入試の「必要な知識は教科書の範囲内だが、
当てはめるだけでは解けず、基本事項を結び付ける発想が要る」問題が手本になる。東大入試が教科書の範囲を超える概念を
問題文の中で定義し、高校生に読めるように作ってあるのは、どの段階でも同じように真似る。

**難易度は自分で選ばない。** 指定がなければ `./script/level.sh <lang>/<type> ...` を実行し、
出力された組ごとの抽選結果（`LANG/TYPE<TAB>LEVEL`）で書く。非対話実行では引数に抽選済みの値がある。
確率は1段ごとに黄金比で割った値で、組ごとに独立に抽選される。

* **過去の傾向は完全に無視する。** 直近の難易度の分布も、同じ日の他の組の難易度も見ない。
  15問すべてがクジラの日も、すべてがハリネズミの日も、その通りに書く。偏りを均さない
* 抽選された難易度が、そのお題に合わないと感じても変えない。お題の中から、その重さに合う切り口を選ぶ
  （同じ「整数の除算」でも、基礎なら切り捨ての向きをそのまま問い、特級なら除算を何度も繰り返す処理の結果を、
  1回ずつ追わずに見抜く見方を見つけさせる）

#### 各段階の基準

**難易度は下の絶対的な基準で作る。過去問との比較（相対）では決めない。** 手順2で直近ページを読むのは
書式とトーンを合わせるためで、難易度の物差しにはしない。過去ページの難易度は旧基準（基礎・初級・中級・上級、
概念の個数と推論の段数で数えた）で付いているので、なおさら物差しにならない。

**段階を分けるのは、知識の量ではなく、答えに着くまでに読者が自分でしなければならないことである。**
珍しい知識やコードの長さでは重さを出さない。READ・DEBUGのコードは21行以内に収め（§3「コードを短く保つ」）、
その深さを21行に収められない切り口は、その難易度に合う別の切り口に替える。

| 段階 | 作問の姿勢 | 読者が自分ですること | 誤答への誘導 |
|---|---|---|---|
| 基礎 | 教科書の重要事項と典型的な形が身に付いているかを問う | 知っている規則を正確に思い出し、順に当てはめる | ほぼなし。知識の抜けがそのまま誤答になる |
| 標準 | 頻出の形に、条件の変更やひねりを1つ加える | 条件を読み取り、知っている規則のうちここで使うものを選ぶ | 見覚えのある形からの自然な誤読が1つ |
| 高度 | 典型を発展させ、複数の論点を同時に扱わせる | 作用し合う規則を同時に扱い、組み合わせて最後まで解き切る | 規則を1つだけ使って考えたときの誤答が、規則ごとにある |
| 特級 | 見たことのない状況を出し、解き方そのものを組み立てさせる | 解き方が示されていない中で、突破口になる見方を見つける | 順に追う、または典型に当てはめると着く誤答 |

* **ハリネズミ（基礎）— 再現する力。** 基本事項と基本的な解き方が定着しているかを問う。教科書の重要事項や
  典型的な形を正面から出してよい。答えに要るのは、知識を正確に思い出して順に当てはめることで、難解な発想は要らない。
  知識が抜けていればそのまま間違え、知っていれば迷わず解ける。ただし教科書の例の丸写しにはせず、数行はコードを
  自分で追わせる。例: 整数除算の切り捨ての向き、`continue` で飛ばされる行、所有権が移ったあとの変数
* **孔雀（標準）— 応用する力。** 見覚えのある形に、条件の変更やひねりを1つ加える。覚えた答えをそのまま書くと
  間違え、条件を読み取って、知っている規則のどれをここで使うかを選ぶ必要がある。自然な誤読が1つあり、
  条件を読み落とすとそこへ着く。例: よく知った `switch` に `break` の無い腕が1つ混じる、見慣れたループに
  空の入力が来る、参照で受けた値が一時オブジェクトだった
* **バイソン（高度）— 統合する力。** 典型を発展させ、2つ以上の規則が同じ箇所で作用し合うようにする。
  個々の規則を知っているだけでは解けない。1つの規則で考えて出した答えは、もう1つを合わせると覆る。
  どの規則が効くかを選び、それらを組み合わせて最後まで解き切る必要がある。もっともらしい誤答が規則ごとにある。
  有名な罠を、それだけでは答えが出ないように別の規則と絡めたものはここに入る
* **クジラ（特級）— 発見する力。** 読者が見たことのない状況を出し、解き方そのものを組み立てさせる。
  コードを見ても、何を追えば答えが出るかがすぐには浮かばない。上から順に追うだけでは答えに着かないか、追い切れない。
  複数の基本事項を結び付ける見方（ループを通して変わらない性質、対称性、値が決まる場所からの逆算など）を
  自分で見つけたとき、初めて一気に解ける。答えを見た読者が「知らなかった」ではなく「知っていたのに、
  そう見ればよいとは思い付かなかった」と感じるものが特級である。
  **有名な罠をそのまま出したものは、絡む知識がいくつあっても特級ではない**（典型の再現なので基礎か標準、
  典型を発展させたものでも高度まで）。手数の多い追跡（8回の挿入を1回ずつ追う、など）も、それだけでは特級にならない。
  特級にするのは、追跡を省く見方が1つあり、それに気付くかどうかで解けるかが決まるときである

**難易度を上げるときは、珍しい知識を足さずに次の方法で上げる:**

* 概念同士を組み合わせる
* 普通に見えるコード同士を干渉させる
* スコープをまたぐ、ライフタイムをまたぐ
* 呼び出し側と定義側の認識をずらす
* 静的な構造と実行時の流れを交差させる
* （特級）解き方を示す手がかりを消す。何を追えばよいかを教える変数名・コメント・問題文の言い回しを置かない

**答えに作用しない要素は数えない。** コードに置いた規則でも、答えを変えない目くらまし（2026-10-27の Haskell READ の
`repeat` と遅延評価がそうで、`take` が文字数で切ることだけで答えが出る）は、段階を上げる材料にならない。

## 1. 雛形生成（script/content.shを使う）

Bashで実行する。上書きはしない・冪等なので、同じ日付で再実行しても安全。

```bash
./script/content.sh new <DATE> <lang>/<type>
```

* 出力が `created: ...` なら新規雛形ができている。`skip (already exists): ...` の場合は
  既にそのファイルが存在する——**中身を確認**し、`TODO:` が残っていなければ既に公開済みの
  本物のページなので、その組は作らずに飛ばし、最終報告でそう伝える
  （公開後のページは編集しない、という方針は最優先で守る。§7.1）。`TODO:` が残っていれば、
  作りかけの雛形なのでそのまま続きを書いてよい。
* `archived: ...` で対応する `archive.html` にも自動で1行追加されている。この行は自分で
  触らない（スクリプトが冪等に処理済み）。

## 2. 直近ページをスタイルの参考にする

同じ `{lang}/{type}/` の直近1〜2件（`ls {lang}/{type}/*/*/*.html | sort | tail -2`。ページは年・月のディレクトリに分かれている）を
読み、次を体で覚える。**その組にまだ1ページも無いとき**（Zigの初日がそう。`ls` は「No such file or directory」で
失敗するが、異常ではない）は、同じ種別のほかの言語の直近ページを読む。言語に固有のこと（ファイル名、コードの見た目）は
下の規則と §3「Zig（0.17）の書き方と資料」に従う：

* `code-filename` の命名規則（C/C++/Rust/Zigはsnake_case、Haskellはモジュール名慣習のPascalCase）
* 問題文・解説文の分量感とトーン（**形式は §3「種別ごとの問題文とコードの形」が優先する。**
  直近ページはそこに書かれた規約より前の古い形のことがある——過去ページは直さない）
* `<title>` と `data-topic`（15字以内）の言い切り方——直近ページで実際の長さの感覚をつかむ。
  ただし `meta description` は2026-09-23以前のページでは英語なので、そこは真似ない
* コードの見た目（インデント幅、改行の位置、`int* p` の `*` の位置、Haskellの先頭カンマなど）は
  直近ページではなく**整形ツール（§4「整形する」）に従う**。2026-10-20以前のページは整形規則より前の形で、
  1行の `for` 文や `int *p` が残っているが、真似ない
* ページの骨組み（問題文・入出力例・`<details>` の形）は直近ページではなく**雛形に従う**。雛形は種別ごとに
  `script/template-read.html` / `template-write.html` / `template-debug.html` があり、
  `content.sh` が種別に合うものを使う。2026-09-28以前のWRITE（例を問題文に埋め込む）・DEBUG（解説が段落だけ）は
  古い形なので真似ない

## 3. 中身を書く（唯一の創造的な作業）

雛形ファイル（`{lang}/{type}/{年}/{月}/{date}.html`）の `TODO:` を全て埋める。Editツールを使うこと
（雛形全体をWriteで作り直さない——nav/JSON-LD/footerは既に正しく生成済み）。

**言語の使い分け（このリポジトリの確定ルール、doc/basic-design.md §1.5 参照）**:

* `<p class="question">` の本文、`<div class="answer-body">` 内の説明文(`<p>`) → **日本語**
* `<title>`、`meta description`、`data-topic`、JSON-LDの `about.name` と `description` →
  **日本語**（英語の術語を混ぜてよい。「値渡しで起きる切断」のように）。
  読者もクエリも日本語なので、ここを英語にすると検索から取りこぼす
* `data-tags` と JSON-LDの `keywords` → **英字のスラッグ**（下記「お題のメタデータ」）
* それ以外すべて（`code-filename`、コード本体とそのコメント、nav、
  `<summary>Answer</summary>`/`<summary>Reference</summary>`ラベル、footer） → **英語のまま**
* 2026-09-23以前のページの `meta description` は英語のままである（2026-09-24の一括投入で
  直したのはタイトルとお題のメタデータだけ）。新しいページでは日本語で書く
* `<html lang="ja">` は雛形の時点で既にセット済み。触らない
* JSON-LDの `"inLanguage"` は `"ja"` のまま（雛形は既にそうなっている）

**書く前に設計する。** コードを書き始める前に、次の4つを決める。コードはその設計を
最短で実現するものとして書き、解説はこの推論経路に沿って書く。

1. 答えの核（1文。同じ言語の他の2問の核と重ねない。§0「お題リスト」）
2. 抽選された段階で読者に求めること（§0「各段階の基準」の表の「読者が自分ですること」の列）。
   特級なら、突破口になる見方を1文で書く。書けないなら、特級の切り口ではない
3. 想定される誤答と、そこへ導く自然な読み方（数と強さは §0「各段階の基準」に合わせる）
4. 正解までの推論経路

**書いたあとに段階を確かめる。** ページを書き終えたら、推敲の前に、出来上がったコードと解説を読み直して次を確かめる。
1つでも外れたら、難易度は変えずに切り口から作り直す（§0「難易度」）。

* 解説の推論経路で読者がしていることが、抽選された段階の「読者が自分ですること」と一致するか。
  基礎の問題に発見が要っていないか。特級の問題が、規則を順に当てはめるだけで解けていないか
* 答えに作用しない要素（目くらまし）を、段階の材料に数えていないか
* 有名な罠を、そのまま特級や高度にしていないか
* 同じ言語の他の2問と、答えの核が重なっていないか

**良問の条件。** どの問題も次を満たす。

1. 正解は一意である
2. 未定義動作に依存しない
3. 処理系依存にしない
4. 実行しなくても論理的に解ける
5. 専門的な暗記を要求しない
6. 問題文に嘘や不自然な前提を置かない
7. コードはできるだけ短くする（`ponytail.md`）
8. 難しさの中心を1か所に集中させすぎない
9. 単なるタイプミス探しにしない
10. 正解を知った後には、基本事項から自然に説明できる

2と3は、READでは出力そのものに適用する。DEBUGではバグの症状が未定義動作や処理系依存であってよいが、
**原因と直し方は一意で、処理系に依らず基本事項から説明できる**こと（下の「DEBUG」）。
**DEBUGのコードは必ずコンパイルが通る**（下の「DEBUG」）。

特に狙うのは「知らなかったから解けない」ではなく、**「知っていた知識を、そこに適用することに
気付かなかった」**という失敗である。

### 読者の前提知識と、それを超える知識の定義

東京大学の入試問題は、高校の教科書の範囲を超える概念を使うとき、名前を出して終わりにしない。
問題文の中で「〜を…という」と定義してから問い、高校生が問題文だけで読んで解けるように作ってある。
Namaranもこの作り方をなぞる。難しさは基本事項の組み合わせで出し（§0「難易度」）、読めないことで出さない。

**読者の前提知識は、次の二つだけとする。**

* その言語を日常的に書くプログラマの知識（doc/requirements.md §6）
* 日本の高校の教科書の範囲の数学・理科・社会（素数、最大公約数、余り、順列・組合せ、確率、数列、
  ベクトル、指数・対数、集合の要素の個数、等速運動など）

**前提知識を超える知識（包除原理の一般形、法 p における逆元、グラフの用語、偶数丸め、ISO週番号など）が
問題を読む・解くのに要るなら、問題文の中で、前提知識の言葉で説明する。** 名前を知らない読者が、説明だけで
問題を読んで解けるようにする。**解き方そのものの名前**（ユークリッドの互除法、フェルマーの小定理など）は答えを漏らすので、
問題文に書かない。言語仕様やプログラミングの用語（整数昇格、借用、遅延評価）は問題が試す知識そのものなので、
この説明の対象にせず、問題文で名前も出さない（下の「お題のメタデータ」）。

**学術用語は使わないのが既定である。** 東大入試が定義するのは問題を読むのに要る概念であって、用語を覚えさせるためではない。
前提知識の言葉で書けるなら、そう書く（「異なる n 個から k 個を選ぶ組合せの数」で足りるところに「二項係数（binomial coefficient）」を
添えない）。学術用語を使ったほうが問題文や解説がすっきりする場合に限り使ってよいが、**使ったら必ず脚注を付ける。**
脚注は解説の中にしか置けない（`script/verify.sh` が問題文の脚注を落とす）ので、問題文で使った用語は解説でも必ず触れ、
その初出に脚注番号を付ける。脚注の書き方は `/humanizer-ja-tech`（同Skill §8「読者の前提知識と、それを超える知識」）にある。

**問題の質の基準**（doc/requirements.md §7・§9・§11・§24を必ず踏まえる）:

* **面白くする。** 無難な教科書の例題（フィボナッチ、階乗、FizzBuzz の類）で済ませず、次のどれかを狙う
  （requirements.md §11「面白さ」）:
  * その言語らしさが見える——同じテーマでも5言語で違う姿になる切り口を選ぶ。C の呼び出しスタック、
    C++ のテンプレートと`constexpr`、Rust の所有権とパターン、Haskell の遅延評価、Zig の `comptime` と
    明示的に渡すアロケータ、のように、その言語でしか書けない・その言語だから起きることを主役にする
  * 意外だが必然——一瞬「え？」となり、仕様を思い出すと「そうなるしかない」と腑に落ちる
  * 美しい——数行に書き方の美しさや言語設計の意図が表れている
  * 身に覚えがある——実務で誰もが一度は踏む罠
* ただし面白さのために、抽選された難易度（§0「難易度」、要件定義 §7）と答えの明確さ（§9）を曲げない。仕様の隅の暗記勝負は面白さではない
* READ: 答えが言語仕様上明確なこと。未定義動作・処理系依存の挙動を「何が出力される？」で
  問わない（それはDEBUG向き）
* WRITE: 唯一の正解がない場合、掲載する実装は「参考実装(Reference)」として書き、
  「これが唯一の正解ではない」旨に触れる
* DEBUG: **コンパイルは通るが、重大な欠陥を抱えたコード**。実務で起きうる最小限のバグで、直し方も最小限の変更で（問題文の形は下記）。
  原因と直し方は一意に決まるようにする（直し方が何通りもありうるなら、問題文で症状を絞る）
* 知識マウントにしない。「ああ、そうだった」を生む問題を選ぶ。既存アーカイブと話題が
  かぶらないよう、手順2で見た直近ページと露骨に同じ切り口は避ける
* コード中の `<` `>` `&` は必ず `&lt;` `&gt;` `&amp;` にエスケープする
* `<pre class="code"><code>` にはエスケープ済みのプレーンなコードだけを書き、色付けの `<span>` は手で書かない（次の「ハイライトを付ける」でスクリプトが付ける）
* `code-filename` はお題に沿った名前を、対象言語の命名規則で

### コードを短く保つ（ponytail）

コードは `ponytail.md` の規律で書く。要点：

* **READ・DEBUGの `<pre class="code">` は合計21行以内**（空行・コメント・`#include`・`import` も数える。
  解答の `<details>` 内は数えない）。`script/verify.sh` が数えて、超えたら落とす
* 超えたら**作問ミス**。空行を消す・1行に詰める・答えに要る行を検証用ソースへ隠す、で収めない。
  `ponytail.md` の手順で、問う規則を1つに絞った別の切り口から作り直す
* WRITEは元からシグネチャだけなので対象外。ただし参考実装も同じ規律で短く書く

### 種別ごとの問題文とコードの形

読む側の負担をどこに置くかは種別で違う。READはコードを読ませる問題なので問題文は短く、
WRITE/DEBUGは**コードを説明の置き場にしない**——書き始める前にコード中の散文を目で拾わせない。

共通：

* 骨組みは雛形（`script/template-{type}.html`）がすでに持っている。TODOを埋めるだけにし、
  要素を足したり組み替えたりしない
* **例を `<pre class="code">` に入れない。** 検証（§4）は `<pre class="code">` の全行が検証用
  ソースに含まれることを要求するので、そこに例を置くと検証が通らない
* 例は1行に収まる短いものを選ぶ。収まらないなら、収まる入力を選び直す

#### READ — そのまま問う

コードを読んで挙動を追わせる。問題文は雛形に固定で入っている「これは何を出力するでしょうか?」のまま
触らない。書くのはコードと解答だけ。

* **入出力例は書かない。** コードが入力そのもので、例を足すと答えが漏れる
* 出力の行数や形式のヒントも足さない
* 解答は、最初の段落で出力そのものを言い切り（「<code>011</code> です。」）、次の段落から
  推論の順に理由を書く

#### WRITE — 問題文は言葉だけ、例は入出力例の枠に

**`// write this: ...` のような指示コメントをコードに書かない。**

* `<pre class="code">` に置くのは**シグネチャと閉じ括弧だけ**で、本体は空にする
  （Haskellは型シグネチャの行だけ）。関数を書くのに必要な型・データ定義があれば、それも置く
* 置いた行は、`名前.ok.拡張子` の参考実装と**1文字も違わない**ようにする（検証（§4）は
  掲載コードの各行が検証用ソースに含まれることを確認する。シグネチャがずれると落ちる）
* `<p class="question">` には、何を返すものかを1〜2文と、境界条件（空・0個・1個のとき）を
  言葉で書く。**例を問題文に混ぜない**
* 例は `<div class="examples">` に**2〜3組**書く。1組が1つの `<div class="example">` で、
  `入力例 n` と `出力例 n` が横に並ぶ（狭い画面では縦に積まれる）。3組目は2組目の
  `<div class="example">` を複製し、ラベルの番号を `3` にする。境界条件の例を1つ含める
* 入力例には関数の呼び出し式（または標準入力）を、出力例には返り値（または標準出力）を、
  `<pre class="io"><code>` の中にそのまま書く。`<` `>` `&` はエスケープする。
  `→` や説明文は書かない。値は参考実装で実際に確かめたものを書く
* 入力が呼び出し式やリテラルで書けない（ハッシュ表・木・構造体の中身など、組み立てるのに何行も要る）ときだけ、
  問題文の最後に記法を1文で決め（「例では、表に入れたキーと個数を、入れた順に `{キー: 個数}` で書きます」）、
  その記法で書く。記法は値の並びを示すだけにし、解き方の手がかり（どの枠に入るか、など）を書き込まない

```html
  <p class="question">
    リストの隣り合う2要素の和を順に並べたリストを返す <code>movingSums</code> を書いてください。要素が1つ以下のときは空リストです。
  </p>

  <div class="examples">
    <div class="example">
      <p class="example-label">入力例 1</p>
      <pre class="io"><code>movingSums [1,2,3,4,5]</code></pre>
      <p class="example-label">出力例 1</p>
      <pre class="io"><code>[3,5,7,9]</code></pre>
    </div>
    <div class="example">
      <p class="example-label">入力例 2</p>
      <pre class="io"><code>movingSums [7]</code></pre>
      <p class="example-label">出力例 2</p>
      <pre class="io"><code>[]</code></pre>
    </div>
  </div>
```

#### DEBUG — コンパイルは通るが、重大な欠陥を抱えたコード

**DEBUGのコードは必ずコンパイルが通る。** コンパイルエラーを直させる問題は作らない
（コンパイラが場所を教えてくれる欠陥は、読む力を試さない）。欠陥は実行して初めて表に出るもので、
しかも**重大**であること——誤った結果を黙って返す、データを壊す・失う、未定義動作、
クラッシュ、ハング、リソースの枯渇・漏れ、のどれか。見た目の不揃い、無駄な処理、
警告が出るだけ、といった軽微なものはDEBUGにしない。Rustのように所有権・借用の誤りが
コンパイルエラーになる言語では、コンパイルを通った先で起きる欠陥（`RefCell` の二重借用による
panic、整数のオーバーフロー、デッドロック、論理の誤りなど）を選ぶ。Zigでは、Debugビルドの安全検査が
止める illegal behavior（整数のオーバーフロー、範囲外アクセス、`unreachable` への到達など）はクラッシュとして、
`std.testing.allocator` が捕まえる解放し忘れはリソースの漏れとして扱える。

検証用ソースは `名前.bug.拡張子`（コンパイルが通る壊れた版）と `名前.ok.拡張子`（直した版）の
組にする。DEBUGに `名前.ng.拡張子` は置かない（§4。置くと検証で落ちる）。

WRITEと同じく、バグの在処や直し方をコメントで示さない。コードが満たすべき仕様や意図をコメントに書くことも
しない（2026-10-27の C++ DEBUG の `// 2-byte length field, big-endian` は、コードと食い違う仕様を書いた時点で
欠陥の在処を指している）。意図は問題文の1文目に書く。コードは実務で見かける形のまま置く。

**問題文**には次の順で書く：

1. そのコードが何をするつもりのものかを1文
2. **入力例** — 引数・標準入力・呼び出し方のどれか1つに決めて書く
3. **いまの出力** — 実際に `名前.bug.拡張子` を動かして観測した文字列。想像で書かない
4. **本来の出力** — `名前.ok.拡張子` の実行結果

* 未定義動作やクラッシュで出力が定まらないバグは、特定の文字列を断定しない。観測した範囲を
  「`3` が出ることもあれば落ちることもある」のように書く
* 「いまの出力」は `名前.bug.stdout` に置いて検証に照合させる（§4）。想像で書くと検証で落ちる

> 連続する同じ値を `(値, 個数)` にまとめる `runs` です。`runs [1,1,2,2,2,3]` は
> `[(1,2),(2,3),(3,1)]` になるはずが、いまは `[(1,2),(2,3)]` が返り、最後の連続が落ちます。

**解答は語らずに、Wrong → Right の順で見せる。** 雛形の `<div class="answer-body">` は次の形になっている。
段落を積み重ねて経緯を物語る書き方（「まず〜を見ると……次に〜なので……」を何段落も続ける）はしない。

1. `<h3 class="wrong">Wrong</h3>` — 問題のコードから**欠陥のある箇所だけ**を抜き出した
   `<pre class="code">`（関数全体を貼り直さない。数行に絞る。`名前.bug.拡張子` の行そのまま）。
   続く `<p>` で、どう間違っているかを書く：どの入力で、どの行が、何を起こし、それがなぜ
   「いまの出力」になるか。1〜2段落
2. `<h3 class="right">Right</h3>` — 同じ箇所を直した `<pre class="code">`（`名前.ok.拡張子` の行そのまま）。
   最小限の修正でよく、同じ欠陥を二度と作らない書き方があるなら、それをリファクタリング例として示してよい
   （その場合も ok ファイルに入れて検証する）。続く `<p>` で、なぜこれで直るかを書く。1〜2段落
3. 脚注 — 豆知識（歴史的経緯、規格の文言、処理系ごとの違い、同じ欠陥の有名な実例など）が
   あれば、本文の該当箇所に `<sup class="fn-ref">1</sup>` を置き、雛形の `<ol class="footnotes">` に書く。
   問題文か解説で学術用語を使ったなら、その脚注は省けない（§3「読者の前提知識と、それを超える知識の定義」）。
   どちらも無ければ `<ol>` ごと消す。本文の流れに要る説明を脚注に逃がさない

```html
      <h3 class="wrong">Wrong</h3>
      <pre class="code"><code>……欠陥のある数行……</code></pre>
      <p>……どう間違っているか……</p>
      <h3 class="right">Right</h3>
      <pre class="code"><code>……直したコード……</code></pre>
      <p>……なぜ直るか……<sup class="fn-ref">1</sup></p>
      <ol class="footnotes">
        <li>……豆知識……</li>
      </ol>
```

抜き出した行は、ブロック全体を同じ幅だけ左に詰めてよい。1行だけインデントを変えるのは不可
（検証は、行どうしの相対的なインデントが整形済みの検証用ソースと同じかを照合する）。
Wrong/Right の `<pre class="code">` は `<details>` の中なので21行の制限には数えないが、
検証（§4）の「掲載コードの各行が検証用ソースに含まれる」には掛かり、ハイライトも必要。
`script/verify.sh` はDEBUGの解答が Wrong＋コード → Right＋コード の順になっているかも確かめる。
2026-09-28以前のDEBUG（コンパイルエラーの問題、段落だけの解説）は古い形のまま残す——公開後のページは直さない。

### Zig（0.17）の書き方と資料

Zigは1.0より前の言語で、リリースのたびに標準ライブラリのAPIが変わる。言語標準の文書は無く、
CLAUDE.md の表の版（0.17.0）のコンパイラと言語リファレンス（langref）が仕様である。記憶にあるZigの書き方は
古い版のものであることが多いので、思い出して書かない。

* **書く前に資料で確かめる。** 使う標準ライブラリの宣言と組み込み関数は zig-docs MCP
  （[zig-mcp](https://github.com/zig-wasm/zig-mcp)）で引く。検証に使うのと同じ `zig` から資料を出している

  | ツール | 使い方 |
  |---|---|
  | `search_std_lib` | `std` の宣言を名前で探す（例: `ArrayList`、`Allocator`） |
  | `get_std_lib_item` | 完全修飾名（`std.mem.Allocator.dupe` など）の説明・シグネチャ・ソースを読む |
  | `get_builtin_function` | 組み込み関数（`@typeInfo`、`@fromBackingInt` など）の説明を読む |
  | `list_builtin_functions` | 組み込み関数の一覧を見る |

* zig-docs が使えないとき（手元のセッションにMCPを入れていない、など）は、`zig env` が示す `std_dir` の下の
  ソースと、`zig` 本体と同じディレクトリの `doc/langref.html` を読む。手元で使うなら
  `claude mcp add zig-docs -- npx -y zig-mcp@1.4.1 --doc-source local --version 0.17.0`（`zig` 0.17.0 が `PATH` にあること）
* **`main` と標準出力。** 0.17 の `main` は `std.process.Init` を受け取り、標準出力には `init.io` を通して書く。
  `std.debug.print` は標準エラーに出るので、READの出力（`名前.stdout` と照合する）には使わない。
  書いたものはバッファに溜まり、最後に `flush` しないと何も出ない。次の形を 0.17.0 で確かめてある：

  ```zig
  const std = @import("std");

  pub fn main(init: std.process.Init) !void {
      var buf: [256]u8 = undefined;
      var stdout_writer = std.Io.File.stdout().writer(init.io, &buf);
      const stdout = &stdout_writer.interface;
      try stdout.print("{d}\n", .{42});
      try stdout.flush();
  }
  ```

  出力の書き方そのものが問いでなければ、ページの `main` はこの形のまま結果を見せるだけにする（`ponytail.md` §1 の6段目）
* **okファイルも完全なプログラム。** ほかの言語と同じく `pub fn main` が要る。Zigのコンパイラは `main` から
  たどれる関数しか型検査しないので、WRITEの参考実装は `main`（かテスト）から必ず呼ぶ。呼ばれない関数の誤りは
  検証を素通りする
* **テストでも確かめられる。** okファイルに最上位の `test` ブロックがあれば、`script/verify.sh` はビルドに加えて
  `zig test` も通す。`std.testing.allocator` は解放し忘れをテストの失敗にするので、確保と解放を扱う問題
  （WRITEの参考実装、DEBUGの直した版）はこれで裏付ける。`init.gpa` のリークは標準エラーに出るだけで、
  終了コードは変わらない
* **警告は無い。** 使わないローカル変数、変更しない `var`、捨てた戻り値はコンパイルエラーになる（ほかの言語の
  `-Werror` に当たるものが最初から有効）。READで「これはコンパイルできるか」を問うなら、この規則が答えになりうる
* 安全検査で止まる illegal behavior を「何が出力されるか」のREADにしない（DEBUG向き。上の「READ」）

### お題のメタデータ

ドリルの画面には日付とファイル名とコードしか出さない。**何を扱う問題かは `<main>` の属性として持たせる。**
`script/topics.sh` がこれを読んで、アーカイブの見出しとタグページ（`/tag/{tag}`）を組む
（doc/basic-design.md §7.1・§7.3・§7.4）。画面に「これはオブジェクトスライシングの問題です」と
書いてしまうと、それ自体が答えの半分になるので、属性で持つ。

雛形の該当TODOを次のように埋める。

```html
<title>値渡しで起きる切断</title>
...
<main
  data-topic="値渡しで起きる切断"
  data-tags="object-slicing virtual-function inheritance"
  data-concepts="オブジェクトスライシング, 値渡し, 仮想関数, object slicing, pass by value"
  data-level="peacock"
>
```

* **`data-topic`** — そのドリルのお題を**日本語15字以内**で言い切る。`<title>` は
  この文字列**だけ**（サイト名も日付も付けない）。JSON-LDの `about.name` も同じ文字列。
  15字はブラウザのタブとGoogleの検索結果が切り詰めずに出す長さで、ここを定型句に使うと
  読む側にも検索する側にも何も伝わらない
* **`data-tags`** — `script/tags.tsv` にあるスラッグを空白区切りで2〜6個（上限8）。
  **まず `./script/topics.sh --tags` で既存の語彙（スラッグと日本語名）を見て、あるものを使う。**
  どうしても無いときだけ、`script/tags.tsv` の末尾に `slug<TAB>日本語の名前`（15字以内）を
  1行足す。スラッグは小文字ASCIIのkebab-caseで、規格・公式ドキュメントの用語をそのまま、
  単数形の名詞句（規則の全文は doc/basic-design.md §7.4）
* **`data-concepts`** — 同じ主題を、人が検索窓に打ち込む言葉で2つ以上。日本語と英語を混ぜ、
  空白を含んでよい。タグが1語で表すものを複数の言い方で持つ
* **`data-level`** — 抽選された難易度（`hedgehog` / `peacock` / `bison` / `whale`。§0「難易度」）を
  そのまま書く。画面の動物のマークは `style.css` がこの属性から描くので、ページにマークのための
  要素や絵文字を書かない。非対話実行では、抽選と違う値を書くとパッチの検査で落ちる

`meta description` は日本語1〜2文・30〜160字で、何を扱うドリルかを具体的に書く
（15字の見出しに入りきらない説明はここに置く）。JSON-LDの `description` に同じ文を、
`keywords` に `data-tags` をカンマ区切りにしたものを書く。
`meta description`（HTML属性）では `<` `&` をエスケープするが、JSON-LD（`<script>` の中身）では
エスケープせず生の `<` `&` を書く（`Vec<String>` のように。既存ページもそうなっている）。

同じ主張が複数の場所に出るので、`script/verify.sh` が一致を機械的に確かめる。ずれていれば落ちる。

**`topics.html` や `tag/` は自分で触らない。** 公開時に別ジョブがスクリプトで組み直す
（非対話実行で変更してよいのは、日付ページ・`archive.html`・`script/tags.tsv` だけ。
それ以外を変更するとワークフローが失敗する）。

### 日本語を推敲する（必須）

1ページの `TODO:` を埋め終えたら、ハイライトと検証の前に `/humanizer-ja-tech` を呼び、そのページを推敲する。
**全ページに行い、省略しない。** 15組を書く日も、最後にまとめてではなく1ページ書き終えるごとに呼ぶ。
何をどう直し、何を変えてはいけないかは、すべてそのSkillにある。

引数は付けずに呼ぶ。対象は書き終えたばかりのページで、Skillの §8 がそう決めている。同じ内容のSkillを
呼び直すと、本文はもう一度読み込まれず「読み込み済み」の短い注記だけが入るので、15ページ分の手順が
会話に積み重ならない（引数を変えるたびに本文が丸ごと足される）。

### ハイライトを付ける

コードを書き終えたら、そのページに対して実行する：

```bash
./script/highlight.sh <lang>/<type>/<YYYY>/<MM>/<DATE>.html
```

* 既存の `<span>` を剥がしてから付け直すので、何度実行してもよい。**コードを直したら毎回再実行する**
* 付いた後のコードを直すときは、そのブロックを span ごとエスケープ済みのプレーンなコードに書き換えてから再実行すればよい
* 引数には作業中の日付ページだけを渡す（非対話実行では他のファイルを変更しない。§0）
* ハイライトが付いていない・スクリプトの出力と違う場合、次の検証が失敗する

## 4. 検証

**ページに載せるコードは、必ず実際にコンパイルし、静的解析を通してから載せる。**
答えに書く出力・「コンパイルエラーになる」・「未定義動作になる」といった主張は、
頭の中で追うだけで済ませず、下の検証用ソースで裏付ける。

### 検証用ソースを置く

リポジトリの外の作業ディレクトリ（ローカルならscratchpad、CIなら引数で指定されたパス）に
`{VERIFY_DIR}/{lang}/{type}/` を作り、そのままコンパイルできる完全なプログラムを置く。
ファイル名は `名前.種類.拡張子`：

| 種類 | 意味 | 使う場面 |
|---|---|---|
| `名前.ok.拡張子` | 警告をエラー扱いにしたビルドと静的解析を通る | READのプログラム、WRITEの参考実装、DEBUGの修正後 |
| `名前.stdout` | `名前.ok.*` を実行した標準出力と完全一致する | READのokには必須。WRITE/DEBUGでも実行結果を示すなら付ける |
| `名前.ng.拡張子` | コンパイルに**失敗**する | 「コンパイルできない」が答えのREAD（**DEBUGには置かない**） |
| `名前.bug.拡張子` | コンパイルは通る（警告可）。解析はしない | DEBUGの壊れたコード（未定義動作・無限ループ・誤った結果など） |
| `名前.bug.stdout` | `名前.bug.*` を厳しいオプションなしでビルドして実行した標準出力と完全一致する | DEBUGの問題文に「いまの出力」を書くとき（**必須**） |

最低限、READは何か1つ、WRITEはok 1つ、DEBUGはok 1つとbug 1つが要る（DEBUGにngがあると落ちる）。

`名前.bug.stdout` は、出力が毎回同じになるバグにだけ置く。未定義動作・ハング・クラッシュのように
出力が定まらないバグには置かない（置くと検証が落ちる）。その場合は問題文でも特定の文字列を
断定しない（§3「DEBUG」）。

* ページの `<pre class="code">` にある行は、コメント行を除きすべて
  その組の ok/ng/bug のどれかに、同じ相対インデントで含まれていなければならない（ブロック全体を
  左に詰めるのは可）。ページ用に書き換えたコードを検証・整形しないまま載せる、ということが
  起きないようにするためのチェック
* `main` や動作確認用の出力、`#[allow(...)]` / `{-# HLINT ignore ... #-}` などは検証用ソースにだけ
  足してよい。ただし抑制は、ページで意図的に見せたい書き方が警告に掛かる場合だけにし、
  理由をコメントで残す。警告が出るのが本当に悪いコードなら、問題の方を直す

使われるツールと、ビルドの厳しさ（`script/verify.sh` の冒頭に詳細）：

* C: `gcc-14 -std=c23 -Wall -Wextra -Wpedantic -Werror -fanalyzer`、実行時はASan/UBSan付き
* C++: `g++-14 -std=c++26 -Wall -Wextra -Wpedantic -Werror`、実行時はASan/UBSan付き
* Rust: `clippy-driver --edition 2024 -D warnings`
* Haskell: `ghc -XHaskell2010 -Wall -Werror` と `hlint`（Warning/Errorで失敗、Suggestionは可）
* Zig: `zig build-exe`（0.17.0、Debug。実行時の安全検査つき）と、最上位の `test` があれば `zig test`
  （§3「Zig（0.17）の書き方と資料」）
* 整形: `clang-format` 23.1.2・`rustfmt`（stable、`style_edition = "2024"`）・`fourmolu` 0.21.0.0・`zig fmt`（zig 0.17.0 に同梱、設定なし）。
  版は `script/format.sh` が確かめ、違えば止まる（版が違うと整形結果が変わるため）

### 整形する

検証用ソースを書いたら、**ページにコードを写す前に**整形する。ok/ng/bug のすべてが対象
（例はRustのREAD。拡張子は言語に合わせて `.c` `.cpp` `.rs` `.hs` `.zig`）：

```bash
./script/format.sh {VERIFY_DIR}/rust/read/*.rs
```

* 規則はリポジトリ直下の `.clang-format`（C/C++）・`rustfmt.toml`（Rust）・`fourmolu.yaml`（Haskell）にある。
  設定ファイルは変更しない。`zig fmt`（Zig）は設定を持たず、Zigの版が整形結果を決める
* ページの `<pre class="code">` には、整形**後**の行をそのまま写す。整形でコードの行が増えて
  READ・DEBUGが21行を超えたら、それも作問ミスとして切り口から作り直す（`ponytail.md` §2）
* `script/verify.sh` は各ファイルが `script/format.sh` の出力どおりかを確かめ、違えば差分を出して落ちる。
  直すときは検証用ソースを直して再整形し、ページに写し直す（ページだけを手で揃えない）
* 構文エラーそのものを問うREADの ng ファイルは、整形ツールが読めないので確認を免除される。
  読める ng ファイル（型エラーなど）は整形が必要
* **整形で消えてしまうレイアウトそのものが問題の主題のときだけ**（ぶら下がりelseを誤解させる
  インデント、Haskellのレイアウト規則など）、その部分だけ整形を止めてよい。理由をコメントで残す。
  抑制の注釈（上記）と同じ扱いで、行数を稼ぐためには使わない

  | 言語 | 止め方 |
  |---|---|
  | C/C++ | `// clang-format off` … `// clang-format on` |
  | Rust | 対象の文・項目に `#[rustfmt::skip]` |
  | Haskell | `{- FOURMOLU_DISABLE -}` … `{- FOURMOLU_ENABLE -}`（行頭に置く） |
  | Zig | `// zig fmt: off` … `// zig fmt: on` |

### 検証を実行する

```bash
./script/verify.sh <DATE> <VERIFY_DIR> <lang>/<type> ...
```

ページ側（JSON-LDが壊れていない、TODOなし、lang-nav/type-navが同じ日付を指す、archive.htmlに行がある、
`<code>` 内がエスケープ済み、掲載コードが検証用ソースに同じ相対インデントで含まれる、READ/DEBUGのコードが21行以内、WRITEの入出力例が `examples` の枠にある、DEBUGの解答が Wrong → Right の形、日本語に推敲で消すはずの型が残っていない、脚注の番号と本文が対応している、ハイライトが `script/highlight.sh` の出力どおり）と、検証用ソース側（上の表と、整形済みであること）を
まとめて確認する。`FAIL` が1つでも出たら§3に戻って直し、全件通るまで繰り返す。

## 5. 報告して止める

対話実行では `git add -A` はしてよいが、**commitはしない**。非対話実行では `git add` も含めて
git操作を一切しない（§0参照）。
最後に日本語で短く報告する：

* 対象（言語/種別/日付）とトピック、難易度
* 新規作成したファイルと、`archive.html` に追加された行
* `/humanizer-ja-tech` の報告（同Skill §8「報告」。推敲で直した主な点、使った学術用語とその脚注、問題文で説明した概念）
* 同じ言語の3問それぞれの答えの核（1文ずつ）と、§3「書いたあとに段階を確かめる」の結果
* 検証結果（`script/verify.sh` の結果）
* commitするかどうかはユーザーの判断を仰ぐ

複数combo分まとめて処理した場合は、comboごとに上記を繰り返し、最後に全体のまとめを1つ添える。
