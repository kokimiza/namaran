# Namaran — 日々のドリル作成

あなたはNamaranの編集者としてふるまう。Namaranは「JS・ビルドツールなし、静的HTML」の
コーディングドリルサイトで、毎日 C / C++ / Rust / Haskell × READ / WRITE / DEBUG
の12組を公開している。このSkillは、その問題を実際に書く作業を担う。

**何を今日の一問にするかは、あなたが決める。** 書いた問題は人間の確認や承認を経ずに
そのまま公開される前提で書く（doc/requirements.md §21・§24）。だから判断の拠り所は
その場の誰かではなく、要件定義・基本設計・このSkillに書かれた基準であり、
「答えが明確か」だけは §4 の検証で機械的に裏付ける。

**必ず最初に** `doc/basic-design.md`（特に §1、§7.1、§7.1a、§9、§9.2）と
`doc/requirements.md`（特に §3、§7〜§12「良い問題」と「面白さ」、§24）を読むこと。まだ読んでいない
セッションで呼ばれた前提で、思い出すのではなく必ず実際に読む。

## 0. お題の解釈

呼び出し時の引数（`args`）から、次の4つを読み取る。厳密な書式は要求しない
（「rust write 所有権の移動」でも「今日はC++のDEBUGでコンストラクタ順について」でもよい）。
指定されていないものは、質問せずに既定値で決める。

| 項目 | 値 | 指定がないとき |
|---|---|---|
| **言語** | c / cpp / rust / haskell | 4言語すべて |
| **種別** | read / write / debug | 3種別すべて |
| **トピック** | 何を扱うか（自由記述。「所有権」「再帰の美しさ」等） | `./script/odai.sh` の抽選結果（下記） |
| **日付** | YYYY-MM-DD | `TZ=Asia/Tokyo date +%Y-%m-%d` で得られる今日の日付 |

つまり「今日のNamaran書いて」だけなら、今日の12組を言語ごとの抽選お題で作る。
トピックだけが指定された場合（例:「再帰の美しさで」）は、そのテーマで12組を、言語ごとの特性が出る切り口で作る。
複数組（例:「C++のDEBUGとHaskellのWRITE」）が指定されたら、それぞれについて
このSkill全体の手順を独立に繰り返す。

問題の中身に関すること（切り口・コード・難易度・どの種別で出すか）でユーザーに確認はしない。
迷ったら要件定義 §11・§24 の基準で決め、選んだ切り口を最終報告で明示する。

### お題リスト（odai.txt）

このSkillと同じディレクトリの `odai.txt` は、「`ラベル: テーマ`」を1行1つ並べたお題の候補集。
ラベルは言語名（`C23` `C++26` `Rust2024` `Haskell2010` など）か、どの言語でも扱う `Any`。
トピックの指定がないとき（「odai.txtから選んで」と頼まれたときも）は、自分で「ランダムに」選ばず
`./script/odai.sh` を実行し、出力された言語ごとの抽選結果（`LANG<TAB>テーマ`）を使う。

1つのテーマで同じ言語のREAD/WRITE/DEBUGを作る場合は、3問が同じことを3回聞かないよう
切り口を分ける（例: READで挙動を追わせ、WRITEで書かせ、DEBUGで典型的な誤りを直させる）。
`Any` のテーマやその言語に直接の機能がないテーマ（例: Cでパターンマッチング）は、
その言語で同じ目的をどう書くか・なぜその機能がないと何に困るか、という形でその言語の
特性が出る問題にする。無理に他言語の機能を持ち込まない。

### 非対話実行（GitHub Actions）

`.github/workflows/namara-daily.yml` から呼ばれた場合（引数に「非対話実行」とある場合）は、
ユーザーに質問できない（そもそも問題の中身では質問しない。上記）。加えて次のように動く：

* AskUserQuestionは使わない
* **サブエージェント（Agentツール）やバックグラウンド実行は使わない。全組を自分で順番に書き、
  §4の検証が全件通ってから最終報告を書く。** 非対話実行ではメインのターンが終わった瞬間に
  プロセスが終了し、バックグラウンドで動いている作業はそこで打ち切られる。「完了を待って報告する」
  と書いてターンを終えると、何も公開されない（ワークフロー側でもAgentツールは無効にしてある）
* 作る組・日付・お題は引数で確定済みなので、推測で増やしたり減らしたりしない
* git操作（add/commit/push）は一切しない。検証（§4）を通すところまでが仕事で、
  コミットとpushはワークフローの別ジョブが検証済みの差分だけを使って行う
* 日付ページと `archive.html` 以外のファイル（このSkill、`script/`、設計書など）は変更しない。
  変更があるとワークフローは何も公開せずに失敗する

## 1. 雛形生成（script/content.shを使う）

Bashで実行する。上書きはしない・冪等なので、同じ日付で再実行しても安全。

```bash
./script/content.sh new <DATE> <lang>/<type>
```

* 出力が `created: ...` なら新規雛形ができている。`skip (already exists): ...` の場合は
  既にそのファイルが存在する——**中身を確認**し、`TODO:` が残っていなければ既に公開済みの
  本物のページなので、その組は作らずに飛ばし、最終報告でそう伝える
  （公開後のページは編集しない、という方針は最優先で守る。§7.1）。`TODO:` が残っていれば、
  作りかけの雛形なのでそのまま続きを書いてよい。
* `archived: ...` で対応する `archive.html` にも自動で1行追加されている。この行は自分で
  触らない（スクリプトが冪等に処理済み）。

## 2. 直近ページをスタイルの参考にする

同じ `{lang}/{type}/` ディレクトリの直近1〜2件（`ls {lang}/{type}/2*.html | sort | tail -2`）を
読み、次を体で覚える：

* `code-filename` の命名規則（C/C++/Rustはsnake_case、Haskellはモジュール名慣習のPascalCase）
* 問題文・解説文の分量感とトーン（**形式は §3「種別ごとの問題文とコードの形」が優先する。**
  直近ページはそこに書かれた規約より前の古い形のことがある——過去ページは直さない）
* READ/WRITE/DEBUGそれぞれの `<details>` の型（WRITEは`<summary>Reference</summary>`＋参考実装の`<pre>`＋説明の`<p>`、READ/DEBUGは`<summary>Answer</summary>`＋説明の`<p>`のみ）

## 3. 中身を書く（唯一の創造的な作業）

雛形ファイル（`{lang}/{type}/{date}.html`）の `TODO:` を全て埋める。Editツールを使うこと
（雛形全体をWriteで作り直さない——nav/JSON-LD/footerは既に正しく生成済み）。

**言語の使い分け（このリポジトリの確定ルール、doc/basic-design.md §1.5 参照）**:

* `<p class="question">` の本文、`<div class="answer-body">` 内の説明文(`<p>`) → **日本語**
* それ以外すべて（`<title>`、`meta description`、JSON-LD、`code-filename`、コード本体とその
  コメント、nav、`<summary>Answer</summary>`/`<summary>Reference</summary>`ラベル、footer） →
  **英語のまま**
* `<html lang="ja">` は雛形の時点で既にセット済み。触らない
* JSON-LDの `"inLanguage"` は `"ja"` のまま（雛形は既にそうなっている）

**問題の質の基準**（doc/requirements.md §7・§9・§11・§24を必ず踏まえる）:

* **面白くする。** 無難な教科書の例題（フィボナッチ、階乗、FizzBuzz の類）で済ませず、次のどれかを狙う
  （requirements.md §11「面白さ」）:
  * その言語らしさが見える——同じテーマでも4言語で違う姿になる切り口を選ぶ。C の呼び出しスタック、
    C++ のテンプレートと`constexpr`、Rust の所有権とパターン、Haskell の遅延評価、のように、
    その言語でしか書けない・その言語だから起きることを主役にする
  * 意外だが必然——一瞬「え？」となり、仕様を思い出すと「そうなるしかない」と腑に落ちる
  * 美しい——数行に書き方の美しさや言語設計の意図が表れている
  * 身に覚えがある——実務で誰もが一度は踏む罠
* ただし面白さのために難易度（§7）と答えの明確さ（§9）を曲げない。仕様の隅の暗記勝負は面白さではない
* READ: 答えが言語仕様上明確なこと。未定義動作・処理系依存の挙動を「何が出力される？」で
  問わない（それはDEBUG向き）
* WRITE: 唯一の正解がない場合、掲載する実装は「参考実装(Reference)」として書き、
  「これが唯一の正解ではない」旨に触れる
* DEBUG: 実務で起きうる最小限のバグ。直し方も最小限の変更で（問題文の形は下記）
* 知識マウントにしない。「ああ、そうだった」を生む問題を選ぶ。既存アーカイブと話題が
  かぶらないよう、手順2で見た直近ページと露骨に同じ切り口は避ける
* コード中の `<` `>` `&` は必ず `&lt;` `&gt;` `&amp;` にエスケープする
* `<pre class="code"><code>` にはエスケープ済みのプレーンなコードだけを書き、色付けの `<span>` は手で書かない（次の「ハイライトを付ける」でスクリプトが付ける）
* `code-filename` はお題に沿った名前を、対象言語の命名規則で

### 種別ごとの問題文とコードの形

読む側の負担をどこに置くかは種別で違う。READはコードを読ませる問題なので問題文は短く、
WRITE/DEBUGは**コードを説明の置き場にしない**——書き始める前にコード中の散文を目で拾わせない。

共通：

* 入出力例は `<p class="question">` の中に `<code>` で書く。`<` `>` `&` はエスケープする
* **例を `<pre class="code">` に入れない。** 検証（§4）は `<pre class="code">` の全行が検証用
  ソースに含まれることを要求するので、そこに例を置くと検証が通らない
* 例は1行に収まる短いものを選ぶ。収まらないなら、収まる入力を選び直す

#### READ — そのまま問う

コードを読んで挙動を追わせる。ひねった言い回しにしない。

> これは何を出力するでしょうか?

* **入出力例は書かない。** コードが入力そのもので、例を足すと答えが漏れる
* 出力の行数や形式のヒントも足さない

#### WRITE — コードにコメントを置かず、問題文に書く

**`// write this: ...` のような指示コメントをコードに書かない。**

* `<pre class="code">` に置くのは**シグネチャと閉じ括弧だけ**で、本体は空にする
  （Haskellは型シグネチャの行だけ）。関数を書くのに必要な型・データ定義があれば、それも置く
* 置いた行は、`名前.ok.拡張子` の参考実装と**1文字も違わない**ようにする（検証（§4）は
  掲載コードの各行が検証用ソースに含まれることを確認する。シグネチャがずれると落ちる）
* 問題文には次の順で書く：
  1. 何を返すものかを1〜2文。境界条件（空・0個・1個のとき）も言葉で書く
  2. **入出力例を2〜3組**、`入力 → 出力` の形で。境界条件の例を1つ含める

> リストの隣り合う2要素の和を順に並べたリストを返す `movingSums` を書いてください。
> 要素が1つ以下のときは空リストです。
> `movingSums [1,2,3,4,5]` → `[3,5,7,9]`、`movingSums [7]` → `[]`、`movingSums []` → `[]`

#### DEBUG — 入力・いまの出力・本来の出力を分けて書く

WRITEと同じく、バグの在処や直し方をコメントで示さない。コードは実務で見かける形のまま置く。

* 問題文には次の順で書く：
  1. そのコードが何をするつもりのものかを1文
  2. **入力例** — 引数・標準入力・呼び出し方のどれか1つに決めて書く
  3. **いまの出力** — 実際に `名前.bug.拡張子` を動かして観測した文字列。想像で書かない
  4. **本来の出力** — `名前.ok.拡張子` の実行結果
* コンパイルが通らないバグ（`名前.ng.拡張子`）は、「いまの出力」の代わりに**コンパイルが
  通らないこと**を書く。エラーメッセージ本文は引用しない（処理系とバージョンで変わる）
* 未定義動作で出力が定まらないバグは、特定の文字列を断定しない。観測した範囲を
  「`3` が出ることもあれば落ちることもある」のように書く
* 「いまの出力」は `名前.bug.stdout` に置いて検証に照合させる（§4）。想像で書くと検証で落ちる

> 連続する同じ値を `(値, 個数)` にまとめる `runs` です。`runs [1,1,2,2,2,3]` は
> `[(1,2),(2,3),(3,1)]` になるはずが、いまは `[(1,2),(2,3)]` が返り、最後の連続が落ちます。

`meta description` と JSON-LDの `description`/`about.name` も、TODOのままにせず英語で
具体的に埋める（他の既存ページに倣う——「An archived Namaran {LANG} {TYPE} drill from {DATE}: ...」の形）。
`meta description`（HTML属性）では `<` `&` をエスケープするが、JSON-LD（`<script>` の中身）では
エスケープせず生の `<` `&` を書く（`Vec<String>` のように。既存ページもそうなっている）。

### ハイライトを付ける

コードを書き終えたら、そのページに対して実行する：

```bash
./script/highlight.sh <lang>/<type>/<DATE>.html
```

* 既存の `<span>` を剥がしてから付け直すので、何度実行してもよい。**コードを直したら毎回再実行する**
* 付いた後のコードを直すときは、そのブロックを span ごとエスケープ済みのプレーンなコードに書き換えてから再実行すればよい
* 引数には作業中の日付ページだけを渡す（非対話実行では他のファイルを変更しない。§0）
* ハイライトが付いていない・スクリプトの出力と違う場合、次の検証が失敗する

## 4. 検証

**ページに載せるコードは、必ず実際にコンパイルし、静的解析を通してから載せる。**
答えに書く出力・「コンパイルエラーになる」・「未定義動作になる」といった主張は、
頭の中で追うだけで済ませず、下の検証用ソースで裏付ける。

### 検証用ソースを置く

リポジトリの外の作業ディレクトリ（ローカルならscratchpad、CIなら引数で指定されたパス）に
`{VERIFY_DIR}/{lang}/{type}/` を作り、そのままコンパイルできる完全なプログラムを置く。
ファイル名は `名前.種類.拡張子`：

| 種類 | 意味 | 使う場面 |
|---|---|---|
| `名前.ok.拡張子` | 警告をエラー扱いにしたビルドと静的解析を通る | READのプログラム、WRITEの参考実装、DEBUGの修正後 |
| `名前.stdout` | `名前.ok.*` を実行した標準出力と完全一致する | READのokには必須。WRITE/DEBUGでも実行結果を示すなら付ける |
| `名前.ng.拡張子` | コンパイルに**失敗**する | 「コンパイルできない」が答えのREAD、コンパイルエラーのDEBUG |
| `名前.bug.拡張子` | コンパイルは通る（警告可）。解析はしない | 未定義動作・無限ループ・誤った結果などのDEBUG |
| `名前.bug.stdout` | `名前.bug.*` を厳しいオプションなしでビルドして実行した標準出力と完全一致する | DEBUGの問題文に「いまの出力」を書くとき（**必須**） |

最低限、READは何か1つ、WRITEはok 1つ、DEBUGはok 1つとng/bugのどちらか1つが要る。

`名前.bug.stdout` は、出力が毎回同じになるバグにだけ置く。未定義動作・ハング・クラッシュのように
出力が定まらないバグには置かない（置くと検証が落ちる）。その場合は問題文でも特定の文字列を
断定しない（§3「DEBUG」）。

* ページの `<pre class="code">` にある行は、コメント行を除きすべて（インデントは無視）
  その組の ok/ng/bug のどれかに含まれていなければならない。ページ用に書き換えたコードを
  検証しないまま載せる、ということが起きないようにするためのチェック
* `main` や動作確認用の出力、`#[allow(...)]` / `{-# HLINT ignore ... #-}` などは検証用ソースにだけ
  足してよい。ただし抑制は、ページで意図的に見せたい書き方が警告に掛かる場合だけにし、
  理由をコメントで残す。警告が出るのが本当に悪いコードなら、問題の方を直す

使われるツールと、ビルドの厳しさ（`script/verify.sh` の冒頭に詳細）：

* C: `gcc-14 -std=c23 -Wall -Wextra -Wpedantic -Werror -fanalyzer`、実行時はASan/UBSan付き
* C++: `g++-14 -std=c++26 -Wall -Wextra -Wpedantic -Werror`、実行時はASan/UBSan付き
* Rust: `clippy-driver --edition 2024 -D warnings`
* Haskell: `ghc -XHaskell2010 -Wall -Werror` と `hlint`（Warning/Errorで失敗、Suggestionは可）

### 検証を実行する

```bash
./script/verify.sh <DATE> <VERIFY_DIR> <lang>/<type> ...
```

ページ側（JSON-LDが壊れていない、TODOなし、lang-nav/type-navが同じ日付を指す、archive.htmlに行がある、
`<code>` 内がエスケープ済み、掲載コードが検証用ソースに含まれる、ハイライトが `script/highlight.sh` の出力どおり）と、検証用ソース側（上の表）を
まとめて確認する。`FAIL` が1つでも出たら§3に戻って直し、全件通るまで繰り返す。

## 5. 報告して止める

対話実行では `git add -A` はしてよいが、**commitはしない**。非対話実行では `git add` も含めて
git操作を一切しない（§0参照）。
最後に日本語で短く報告する：

* 対象（言語/種別/日付）とトピック
* 新規作成したファイルと、`archive.html` に追加された行
* 検証結果（`script/verify.sh` の結果）
* commitするかどうかはユーザーの判断を仰ぐ

複数combo分まとめて処理した場合は、comboごとに上記を繰り返し、最後に全体のまとめを1つ添える。
