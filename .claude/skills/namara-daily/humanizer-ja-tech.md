# 日本語技術文の推敲

目指すのは、読者が「前の文を理解したら、次の文が自然に読めた」と感じる文章である。読んでいる間は日本語そのものを意識せず、技術の内容だけが頭に入る。

そのために要るのは、AIらしい表現を消すことより、事実と事実の関係を順に読者へ渡していくことだ。短い文を並べても読みやすくはならない。関係の見えない短文の列は、関係を組み立てる仕事を読者に押しつける。

## 0. このファイルの使い方

- 推敲の手順は §7 にある。§1〜§6 はその判断基準で、§7 の各パスから参照する。
- 形式(見出しを使うか、入出力例をどう見せるか、脚注の書式、文体)は、呼び出し元のスキルやリポジトリの規約が決める。このファイルが決めるのは言葉の選び方と並べ方で、規約と食い違ったら規約に従う。
- Namaran のドリルページを推敲するときは、先に §8 を読む。

## 1. 優先順位

食い違ったときは上を取る。

1. 技術的な意味を変えない。コード、数値、出力、条件、例外、結論はそのまま残す。
2. 裏付けのない事実を足さない。
3. 読者が理解できる順に並べる(§2)。
4. 文と語を整える(§3、§4)。
5. AI特有の定型を除く(§5)。
6. 要らないものを削る。

「人間らしく」見せるために感想、比喩、冗談、語りかけを足さない。技術文の自然さは装飾からではなく、論理と日本語の流れから生まれる。

人の原稿を推敲するなら、それは編集の素材である。筆者の言い回し、意味のある余談、意図したユーモアは残す。新しい事実や例、歴史的背景、教訓、励まし、「ここがポイントです」式の演出は足さない。自分の下書きを推敲する場合も、足してよいのは読者の理解に要る説明だけで、新しい技術的主張は検証できたものに限る。

## 2. 論理の流れ

### 2.1 既知から新へ進み、前の文の語を次の文の足場にする

文は、読者がすでに知っている情報から始めて新しい情報へ進める。前の文で出た語や概念を次の文の書き出しに使えば、接続詞がなくても文がつながる。

悪い例:

> `uint64_t` への代入は最後に行われます。`p * p` では整数昇格が起きます。

読者は「なぜ急に昇格の話になったのか」と引っかかる。

良い例:

> `p * p` では整数昇格が起きます。昇格によって積は `int` で計算され、その結果があとから `uint64_t` に代入されます。

「しかし」「また」「さらに」「一方で」を並べても、論理はできない。

> また、`int` に昇格します。そのため、オーバーフローします。一方で、代入先は `uint64_t` です。

これは事実を接続詞で貼り合わせただけで、関係は読者が組み立てることになる。前の文の語を受けて書けば、接続詞は要らなくなる。

> `p * p` は `int` で計算されます。この掛け算が `int` の範囲を超えた時点で結果は壊れており、あとから `uint64_t` へ代入しても直りません。

### 2.2 文末に、その文で一番伝えたいことを置く

日本語では文末が着地点になる。既知の情報や細かな条件で文を終えない。

> 整数昇格が行われることが、この問題の原因です。

この文は「原因です」に着地するが、何か問題が起きていることは読者がすでに知っている。伝えたいのは昇格が何を引き起こすかなので、新しい事実で文を終える。

> 演算の前に整数昇格が起きるため、積は `int` で計算されます。

語順を機械的に固定するのではない。各文がどこへ着地するかを意識する。

### 2.3 読者に覚えさせたまま待たせない

主語と述語、条件と帰結、修飾語と被修飾語を遠ざけない。条件や括弧を積み上げてから結論を出すと、読者はそれを全部覚えたまま文末を待つことになる。

悪い例:

> `p` が `uint16_t` で、処理系の `int` が32ビットで、整数昇格によって値が `int` に収まる場合、この積は……

結論を先に出す:

> この環境では、`p * p` は `int` で計算されます。32ビットの `int` は `uint16_t` のどの値も表せるので、整数昇格で両方のオペランドが `int` になります。

修飾語はかかる語の近くに置き、どの語がどこにかかるかが一読で決まるようにする。

### 2.4 段落は論点が変わるところで切る

一段落には、一つの問い、説明、主張、または手順を持たせる。文数や行数では切らない。

段落の展開を毎回同じ型(何が起きる、なぜ、例、まとめ)にしない。型をなぞると、最後に要らないまとめが付く(§5.4)。一文だけの段落を演出に使わない。

## 3. 文の組み立て

### 3.1 一文に一つの意味関係を持たせる。一文一事実にはしない

事実を一つずつ句点で切ると、関係が見えなくなる。

悪い例:

> `p` は `uint16_t` です。整数昇格が起きます。`int` になります。掛け算されます。その後 `uint64_t` に代入されます。

良い例:

> `p` 自体は `uint16_t` ですが、掛け算の前に整数昇格が起きるので、`p * p` は `int` で計算されます。結果が `uint64_t` に入るのはそのあとです。

原因と結果、条件と挙動、比べる二つ、操作と結果のような一つの関係なら、一文に収めてよい。関係は「〜ため」「〜なら」「〜が」「〜すると」「〜のあとで」のような文法で示す。句点は意味の関係が完結したところで打ち、文字数では打たない。

### 3.2 長い文は、分ける前に削る

長い文を見つけても、すぐに句点を足さない。次の順に試す。

1. 要らない語と重複を削る
2. 語順と修飾関係を直す
3. 本筋でない情報を脚注へ移す(§6.3)
4. それでも長ければ文を分ける

### 3.3 文の長さと文末は、意味に任せて揺らす

同じ型の文が続くと、読者は内容より文のリズムに気を取られる。です・ます調では「〜です。〜です。〜です。」「〜します。〜します。」が特に続きやすい。

直すときは、文末の言い回しを替えるより先に、関係を見つけて文をつなぐ(§3.1)。文の数が減れば、同じ文末の連続も減る。そのうえで残った連続には「〜からです」「〜ません」「〜のは〜です」のような形を使う。です・ます調の中の体言止めは浮くので使わない。

短い文は断定や話の転換に使い、説明には必要な長さを使う。長短を人工的な配置パターンにはしない。意味に沿って書けば、リズムは結果としてついてくる。

## 4. 語と表記

- 同じ概念には同じ語を使う。「引数」「パラメータ」「渡した値」を理由なく言い換えない。読者は別の語を別の物と受け取る。
- 名詞化を動詞に戻す。「値の取得を行う」は「値を取得する」、「エラーの発生が確認される」は「エラーが起きる」。技術用語は残し、その周りを官僚文にしない。
- 明らかな主語を繰り返さない。「この関数は値を受け取ります。この関数は値を変換します。」は「この関数は値を受け取り、変換した結果を返します。」にする。省くと主語が曖昧になるときは書く。
- 助詞の渋滞をほどく。「クラスのインスタンスのメンバの値の変更」は「インスタンスが持つメンバの値を変えること」のように組み直す。
- 読点は、誤読を防ぐとき、条件節と主節を分けるとき、長い並列を区切るとき、話が転じるときに打つ。主語のあとに毎回打つ癖はつけない。
- 漢字、ひらがな、英数字、inline code が詰まって読みにくければ組み直す。ただし技術用語を無理に和語にしない。
- 文体(です・ます調か、だ・である調か)は一つに揃える。どちらにするかは媒体が決める。
- 本文では次を使わない: em dash `—` と en dash `–`、飾りの `--`、絵文字、意味のない太字、過剰な感嘆符、要らない引用符、全角英数字。
- コード、inline code、コマンド、URL、パス、正式名称、引用、それに媒体が定めた定型文は、一字も変えない。

## 5. AI文体を除く

どれも、新しい情報を渡さずに読者の注意だけを使う表現である。見つけたら、削っても意味が変わらないかを確かめて削る。

### 5.1 舞台装置

「まず押さえておきたいのは」「ここで重要なのは」「ポイントは」「実は」「一見すると」「興味深いことに」「では見ていきましょう」「深掘りしてみましょう」「覚えておきましょう」。必要な事実から書き始める。

### 5.2 偽の対比

「単なるAではなく、Bです」「Aというだけではありません。Bなのです」。Aだと主張している人がいないなら、Bだけを書く。

### 5.3 誇張

「非常に重要」「極めて」「強力」「本質的」「決定的」「大きな落とし穴」。程度を伝える必要がなければ事実だけを書く。必要なら、形容詞ではなく数値や条件で示す。

### 5.4 言い直しとまとめ

「つまり重要なのは整数昇格です」のように直前の内容を言い直すだけの文は削る。節の最後に「以上から、整数昇格には注意が必要です」のような総括を足さない。最後の具体的な事実で終われるなら、そこで終える。

各文は、読者がまだ持っていない情報か関係を一つ以上足す。

### 5.5 飾りの三項列挙

「正確で、効率的で、堅牢な」のように、整って見せるためだけに三つ並べない。意味の上で三つあるなら問題ない。

### 5.6 語りかけと子ども扱い

「なぜでしょうか?」「不思議ですよね」で毎節を始めない。「難しそうですよね」「安心してください」「簡単です」「初心者でも大丈夫です」も使わない。やさしさは語りかけではなく、説明の順序と語彙で作る。

## 6. 文章の種類ごとに

### 6.1 問題文

文学的な自然さより、何をすれば正解なのかが一読で分かることを優先する。読み終えた読者が次の四つを言えるようにする。

1. 何が与えられるか
2. 何を求められているか
3. どんな条件があるか
4. 何を答えればよいか(出力、戻り値、直す箇所、説明)

背景と要求を分ける。

悪い例:

> 次のコードでは整数型を扱っており、C++には整数昇格という仕組みがあるので少し注意が必要ですが、正しく動くようにしてください。

良い例:

> 次のコードは `p` の二乗を `uint64_t` に保存します。`p = 50000` のとき、正しい値になりません。どこを直せばよいでしょうか?

悪い例は背景と要求が混ざっているうえに、問う内容(整数昇格)を先に教えてしまっている。

- 答えを漏らさない。整数昇格を問う問題に「整数昇格が起きるため」と書かない。問題に要る前提だけを書く。
- 要求をぼかさない。疑問形でも、答える対象が一つに決まっていればよい(「何を出力するでしょうか」「どこを直せばよいでしょうか」)。避けるのは、何を答えればよいかが決まらない問い(「どうすればよいでしょうか」「考えてみてください」)である。命令形と依頼形のどちらにするかは媒体の文体に従う。
- 入力例と出力例は必ず組にする。値は飾りではないので、通常の値、境界の値、バグが現れる値のように、仕様の理解に役立つものを選ぶ。例を増やしすぎない。例の説明で解き方を明かさない。
- 解くのに関係する制約だけを書き、本文に埋もれさせない。
- 余韻や煽りを作らない。「このコードにはどんな罠が潜んでいるでしょうか」「一見簡単そうですが、実は奥深い問題です」。問題が面白ければ演出は要らない。

入出力例や制約をどういう形(見出し、コードブロック、inline code)で見せるかは媒体が決める。

### 6.2 解説文

筆者が知っている順ではなく、初めて知る読者が理解できる順に並べる。基本の流れは次のとおりで、別の順の方が自然なら変えてよい。

1. 読者が観察できる現象(何が出力されるか、何が起きるか)
2. 直接の原因
3. その原因を生む言語仕様
4. コードのどこで壊れるか
5. 直し方と、なぜそれで直るか
6. 必要なら補足(多くは脚注、§6.3)

- 規格や定義から書き始めない。現象を先に置き、そこから理由へ進む。
- 読者が知らなそうな用語は、出したその場で短く説明する。辞書の文にせず、いま見ているコードに結びつける。
  > ここで整数昇格が起きます。`int` より小さい整数型は、演算の前に `int` へ変換されるという規則です。
- 規則と具体例を行き来する。規則を書いたら、このコードの値で確かめ、そこから新しく分かる帰結で締める。最後の一文が規則の言い直しになるなら、それは §5.4 のまとめなので削る。
- 「こう書けば直る」で終えず、なぜ直るかを書く。
  > 左の `p` を先に `uint64_t` へ変換すると、掛け算そのものが `uint64_t` で行われます。
- 比喩でやさしくしても、正式な名前と挙動は残す。「ざっくり言うと」で仕様を置き換えない。
- コードと、それを説明する文を遠ざけない。コードを日本語で読み上げない(「`std::uint64_t{p}` と書いて、std 名前空間の uint64_t 型で p を波括弧初期化して……」)。読者に要るのは、その書き方が何を起こすかである。

### 6.3 脚注

脚注は、本文の論理線をまっすぐに保つための置き場である。補足を増やす口実ではない。

- 本文に残す: 結論、原因、根拠、再現条件、直し方、理解に欠かせない制約。今回の結論を変える例外も本文に書き、脚注に隠さない。
- 脚注に回す: 本題に関係はあるが、読み飛ばしても結論が分かるもの。規格の厳密な文言や条項、処理系やバージョンによる違い、本題では使わない例外、同じ概念の別名、「厳密には」の続き、理解の助けになる歴史的経緯。
- 削る: 面白いだけで本題に寄与しない雑学。
- 括弧の中が一文を超えそうなら、脚注にするか削るかを考える。
- 脚注の文も本文と同じ基準で推敲し、短く書く。

脚注の書式は媒体に従う。Markdown なら `本文[^1]` と `[^1]: 補足。` を使う。

### 6.4 見出しと箇条書き(媒体が使う場合だけ)

- 見出しは内容を予告する。「`p * p` は `int` で計算される」「掛け算の前に型を広げる」のように、見出しだけで要点が分かるようにする。「原因」「ポイント」「なぜ?」「まとめ」のようなラベルだけの見出しにしない。短い記事に見出しを増やしすぎない。
- 箇条書きは、並列する条件、手順、選択肢のように、本当に並列なものに使う。因果を箇条書きにすると関係が消える(「`uint16_t`」「`int` に昇格」「掛け算」「オーバーフロー」と並べても、どれがどれの原因かは書かれていない)。因果は文章で書く。

## 7. 推敲の手順

次のパスを順に通し、一つのパスでは一つの観点だけを見る。後のパスの修正が前のパスの結果を崩すことがあるので、最後に通しで読む。

### パス1: 意味(§1)

- コード、数値、出力、条件、例外が変わっていないか
- 裏付けのない事実を足していないか
- 技術的な内容に手を入れたなら、検証をやり直したか

### パス2: 構造(§2、§6)

- 読者が最初に知るべきことが先にあるか
- 各文が前の文の語を足場にしているか
- 段落ごとに論点が一つか
- 本筋から外れた補足が本文に残っていないか(§6.3)
- 問題文なら、§6.1 の四つを読者が言えるか。答えが漏れていないか
- 解説なら、現象から始まっているか

### パス3: 文と語(§3、§4)

- 一文一事実の短文列になっていないか。逆に、長すぎる文はないか
- 係り受けが遠い箇所、修飾先が曖昧な箇所はないか
- 同じ文末や構文が続いていないか
- 名詞化、助詞の渋滞、用語の揺れ、文体の混在はないか

### パス4: AI文体(§5)

次を探し、残すなら理由を言えるか確かめる。

「重要なのは」「ポイントは」「実は」「一見すると」「単なる〜ではなく」「つまり」「非常に」「〜しましょう」「〜ですよね」、段落末のまとめ、飾りの三項列挙、em dash、意味のない太字。

### 最終確認

通しで一度読み、次を自問する。

- 各文は、読者がまだ持っていない情報か関係を足しているか
- 文と文の間に飛躍はないか。読者に余計なことを覚えさせていないか
- 目で追って、日本語そのものに引っかからずに読めるか
- 「AIらしくない文章」を演じて、砕けた表現や感情を足していないか。技術者が一人の読者に向けて普通に書いた文章になっているか

## 8. Namaran のドリルページで使うとき

形式は、同じディレクトリの `SKILL.md` §3 と `doc/basic-design.md` §7.1 が決めている。このファイルで直すのは、その枠の中の日本語だけである。

### 推敲する箇所

- `<p class="question">` の問題文
- `<div class="answer-body">` の中の `<p>` と、脚注の `<li>`
- `meta description`。JSON-LD の `description` と同じ文なので、片方を直したら両方を直す(`script/verify.sh` が一致を確かめる)
- `<title>` と `data-topic` は15字以内の言い切りなので、推敲で長くしない。変えるなら JSON-LD の `about.name` も揃える

### 文体

です・ます調で統一する。公開済みのページはすべてです・ます調である。

### 変えないもの

- `<code>` の中身、コード、出力の文字列、`data-level`。DEBUG の「いまの出力」は検証用ソースの実行結果と照合されるので、一字も変えない
- READ の定型の問い「これは何を出力するでしょうか?」
- WRITE で正解が一つに決まらない場合の、「掲載したのは参考実装で、唯一の正解ではない」という趣旨の文。演出に見えても `SKILL.md` が求める内容である
- 技術的な内容に手を入れたら、`script/verify.sh` を通し直す

### 形式の制約

- 問題文は一つの `<p>` で書き、見出し、箇条書き、`<pre>` は使わない。入出力例は `<code>` で1行に収め、WRITE は `入力 → 出力` の組、DEBUG は入力、いまの出力、本来の出力の順に書く(`SKILL.md` §3「種別ごとの問題文とコードの形」)。§6.1 の入出力の見せ方より、こちらが優先する。
- 解説は `<p>` の段落で書く。見出しと箇条書きは使わない(§6.4 は適用しない)。
- 脚注は解説の中だけで使い、問題文には置かない。書式は `doc/basic-design.md` §7.1 の HTML(本文の該当箇所に `<sup class="fn-ref">1</sup>`、解説の末尾に `<ol class="footnotes"><li>補足。</li></ol>`)で、Markdown の `[^1]` は使わない。
- リンクは張らない。`script/check-patch.sh` はサイト外へのリンクも `id` 属性も通さないので、本文と脚注をつなぐページ内リンクも書けない。
- 問題文でお題の名前(「オブジェクトスライシング」など)を出さない。名前そのものが答えの半分になる(§6.1「答えを漏らさない」)。
