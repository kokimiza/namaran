# Ponytail — 短いドリルを書く

あなたは怠惰なベテランとして問題を書く。怠惰とは手を抜くことではなく、答えに関係しない行を
1行も書かないことである。Namaranは歯磨きのように数分で終わるドリルで（要件定義 §12）、
読者の時間は問う規則を考えることにだけ使わせる。長いコードを読ませる日は、それだけで失敗である。

## 0. このファイルの使い方

* コードを書き始める前に最後まで読み、§1 の手順で書く
* `script/verify.sh` が「question code is N lines」で落ちたら §2 に従う
* 形式（問題文の書き方、検証用ソースの規約など）は `SKILL.md` が決める。このファイルが決めるのは
  コードの量だけで、食い違ったら `SKILL.md` に従う

## 1. はしご — 上から順に、止まれる段で止まる

1. **問う規則は1つか。** 1問が問うのは1つの規則（バイソン・クジラは複数の規則の「絡み」を1つ）。
   2つ目の話題が混ざっているなら、それは別の日の問題である
2. **この行は答えに要るか。** 問う規則に関係しない行——ログ、防御的なエラー処理、使わない変数、
   念のための2つ目のケース、説明のための中間変数——は消す。消して答えが変わらない行は要らない
3. **現象はもっと小さい入力で起きないか。** 3要素で起きることを10要素で見せない。
   ループ3回で見えるなら3回、1回で見えるなら1回
4. **標準の道具で1行にならないか。** 標準ライブラリや言語機能で書ける処理を自前で書かない
   （問う対象がその自前実装そのものなら別）
5. **型は最小か。** 構造体・クラス・データ型はフィールドもメンバも問いに要る分だけ。
   継承の問題なら基底と派生の2つで足りる
6. **`main` は結果を見せるだけか。** 呼び出して出力する数行に留める
7. **ここまで来て初めて**、残った最小のコードを、その言語の慣用どおりに読みやすく書く

書き終えたら、`<pre class="code">` の行数を数える（空行・コメント・`#include`・`import` を含む。
解答の `<details>` 内は数えない）。**READ・DEBUGは21行以内。** WRITEはシグネチャだけなので対象外だが、
参考実装も同じはしごで短く書く。

## 2. 21行を超えたら — 作問ミス、作り直す

21行を超えたのは、コードの書き方ではなく**切り口の選び方**が間違っている。お題と難易度は変えずに、
§1 の1段目からやり直して別の切り口を選ぶ。

**次の方法で収めてはいけない。** どれも行数だけを誤魔化し、読む負担は減らない。

* 空行を消して詰める、1行に複数の文や宣言を押し込む、慣用から外れた書き方で縮める
* 答えを決める行（READの出力を決める行、DEBUGのバグを再現する行）を、ページから消して
  検証用ソースだけに置く
* コードの一部を問題文の散文に移す（「`f` は `x` を2倍して返す関数とします」）
* 1問を2つの `<pre>` に分ける（合計で数える）

削ってよいのは、検証のためだけにある行（SKILL.md §4 の、動作確認用の出力や抑制の注釈）だけで、
それは元からページに載せない。

## 3. 短くしても削らないもの

* **答えの明確さ。** READなら言語仕様だけで出力が決まること。短くするために処理系依存へ寄せない
* **検証が通ること。** 警告をエラーにしたビルドと静的解析（SKILL.md §4）を通る形を保つ
* **読みやすさ。** 普通のインデント、意味の通る名前、その言語の慣用。1文字変数で詰めるのは
  短さではなく読みにくさである
* **難易度の深さ。** 重さは行数ではなく考える深さで出す（SKILL.md「難易度」）。クジラを21行で
  書けないなら、21行で深さの出る別の切り口を探す。深さを落として収めるのではない

短いコードは結果であって目的ではない。問う規則が1つに絞れていれば、コードは自然に短くなる。
