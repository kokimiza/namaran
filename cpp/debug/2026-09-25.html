pixel_energy.cpp

#include <cstdint>
#include <iostream>
#include <vector>

std::uint64_t energy(const std::vector<std::uint16_t>& pixels) {
    std::uint64_t sum = 0;
    for (std::uint16_t p : pixels) {
        sum += p * p;
    }
    return sum;
}

int main() {
    std::cout << energy({40000, 50000}) << '\n';
}

energyは、16ビットの画素値の2乗和をstd::uint64_tで求める関数です。入力はenergy({40000, 50000})。本来の出力は4100000000ですが、いまの出力は保証されません。手元でビルドして動かすと18446744073514584320のような巨大な値が出ることがあり、-fsanitize=undefinedを付けるとp * pの行で符号つき整数のオーバーフローが報告されます。どの型も符号なしなのに、なぜでしょうか。どう直せばよいでしょうか?

Answer

p * pはstd::uint16_t同士の掛け算に見えますが、算術の前に整数昇格が起きます。int(32ビット)はstd::uint16_tの全ての値を表せるので、両辺はunsigned intではなく符号つきのintに昇格し、掛け算はintで行われます。40000 * 40000 = 1600000000はINT_MAX(2147483647)に収まるので正しく計算できますが、50000 * 50000 = 2500000000は収まらず、符号つきオーバーフロー、つまり未定義動作です。実際の機械ではたいてい-1794967296に折り返され、それをstd::uint64_tのsumに足すときに264を法とした変換で巨大な正の数になります。左辺がstd::uint64_tでも、右辺の型は右辺だけで決まるので守ってくれません。明るい画素が来たときだけ壊れるので、小さい値のテストでは通ってしまいます。直し方は、掛ける前に片方を広い符号なし型にすることです:

sum += std::uint64_t{p} * p;

片方がstd::uint64_tなら、通常の算術変換でもう片方もstd::uint64_tになり、掛け算は64ビットの符号なしで行われます。static_cast<std::uint64_t>(p * p)のように結果を変換しても遅すぎます(あふれるのは変換の前です)。std::uint8_t同士なら255 * 255はintに収まるので同じことは起きず、16ビットで初めて踏む罠です。
