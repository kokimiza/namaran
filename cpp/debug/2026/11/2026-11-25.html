buf_sum.cpp

#include <cstdio>

struct Buf {
    int* data = new int[3]{1, 2, 3};
    ~Buf() {
        delete[] data;
    }
};

int sum(Buf b) {
    return b.data[0] + b.data[1] + b.data[2];
}

int main() {
    Buf b;
    std::printf("%d\n", sum(b));
    std::printf("%d\n", sum(b));
}

Buf は3つの整数を持ち、コピーしても互いに影響しない値として使うつもりの型で、sum はそのコピーを受け取って合計を返します。main で同じ b の合計を2回表示すると、本来は 6 を2行出力するはずが、いまは異常終了します。glibc の環境では標準エラーに free(): double free detected in tcache 2 と出て止まり、AddressSanitizer を付けてビルドすると、2回目の sum の中で解放済みのメモリを読んだと報告して止まります。

Answer

Wrong

struct Buf {
    int* data = new int[3]{1, 2, 3};
    ~Buf() {
        delete[] data;
    }
};

sum は Buf を値で受け取るので、呼ぶたびに b のコピーが作られます。Buf はコピーコンストラクタを書いていないため、コンパイラが用意した暗黙のコピーコンストラクタが使われ、メンバを1つずつ写します。写されるのはポインタ data の値だけで、配列は1つのまま、main の b と引数のコピーが同じ配列を指します。1回目の sum は 6 を返しますが、戻るときに引数のデストラクタがその配列を delete[] します。

2回目の sum が受け取るのは、解放済みの配列を指すポインタのコピーです。そこを読むのは未定義動作で、AddressSanitizer はこの読み出しで止めます。止めずに進むと、2回目の引数のデストラクタが同じ配列をもう一度 delete[] し、glibc がこの二重解放を見つけて異常終了させます。デストラクタで資源を解放するのに、コピーの仕方をコンパイラ任せにしたことが原因です。

Right

#include <vector>

struct Buf {
    std::vector<int> data{1, 2, 3};
};

配列を std::vector に持たせると、Buf の暗黙のコピーコンストラクタは vector のコピーコンストラクタを呼び、要素ごと新しい領域へ写します。解放も vector のデストラクタが自分の領域に対してだけ行うので、Buf にデストラクタを書く必要がなくなります1。引数のコピーが消えても b の配列は残り、6 が2行出力されます。暗黙のコピー代入やムーブも同じく要素ごとに正しく働くので、あとから Buf を代入に使っても同じ欠陥は起きません。

  1. デストラクタ、コピーコンストラクタ、コピー代入演算子のどれか1つを自分で書くクラスは、たいてい3つとも書く必要があるという経験則を「ルール・オブ・スリー」、資源の管理は std::vector や std::unique_ptr のような専用のクラスに任せ、自分のクラスではどれも書かないという方針を「ルール・オブ・ゼロ」と呼びます。生のポインタを残して直すなら、配列を写すコピーコンストラクタとコピー代入演算子を書き足すことになります。
