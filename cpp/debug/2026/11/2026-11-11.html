prefix.cpp

#include <print>

int apply(char op, int a, int b) {
    return op == '+' ? a + b : op == '-' ? a - b : op == '*' ? a * b : a / b;
}

int eval(const char*& p) {
    char c = *p++;
    if (c >= '0' && c <= '9') {
        return c - '0';
    }
    return apply(c, eval(p), eval(p));
}

int main() {
    const char* src = "/-93-41";
    std::println("{}", eval(src));
}

eval は、演算子を2つのオペランドの前に置く書き方で書いた、1桁の整数の四則演算を計算する関数です。この書き方では -93 が 9 − 3 を、/-93-41 が (9 − 3) / (4 − 1) を表します。/-93-41 を渡すと本来は 2 を出力するはずが、いまは手元の g++ でビルドすると 0 を出力します。

Answer

Wrong

    return apply(c, eval(p), eval(p));

2つの eval(p) はどちらも p を進めるので、先に呼ばれたほうが左のオペランドを読みます。ところが C++ は、関数の引数をどの順に評価するかを決めていません。g++ はこの呼び出しで右の引数から評価するため、b に入る eval が先に -93 を読み、a に入る eval が -41 を読みます。

入れ替わりはすべての段で起きるので、-93 は 3 − 9 = −6、-41 は 1 − 4 = −3 になり、全体は −3 / −6 です。int の割り算は0の方向へ切り捨てるので、結果は 0 になります。+ と * はオペランドを入れ替えても値が同じなので、足し算と掛け算だけの式ではこの欠陥が表に出ません。

Right

    int lhs = eval(p);
    int rhs = eval(p);
    return apply(c, lhs, rhs);

別々の文に分けると、前の文の評価は次の文より先に必ず終わります。左のオペランドを読む eval が先に呼ばれることがコードの並びで決まるので、どのコンパイラでも /-93-41 は 6 / 3 = 2 になります。字句を読み進める呼び出しを1つの式の中に2つ並べず、読む順に変数へ受けるのが確実です。1

  1. C++17 で、<< のオペランドや波括弧の初期化子リストなど、いくつかの評価順が左から右に決まりました。関数の引数は対象外で、どれか1つの引数の評価を丸ごと済ませてから次へ進むことだけが保証されています(順序の決まらない引数どうしが入り混じることはないので、未定義動作ではありません)。同じ式を波括弧で Node{c, eval(p), eval(p)} のように書いた場合は、左から順に評価されます。
