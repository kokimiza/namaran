intern.rs

fn intern(name: &str) -> usize {
}

プログラム全体で共有する名前の表に name を登録し、その番号を返す intern を書いてください。初めて見る名前には、登録した順に 0 から番号を振ります。登録済みの名前には、前と同じ番号を返します。intern は複数のスレッドから同時に呼ばれてもよく、呼び出し側が渡した文字列は呼び出しのあとで捨てられることがあります。static mut と外部のクレートは使いません。例の入力は同じプログラムの中で上から順に呼ぶもので、出力はそれぞれの戻り値です。

入力例 1

intern("x")

出力例 1

0

入力例 2

intern("y")

出力例 2

1

入力例 3

intern("x")

出力例 3

0

use std::sync::Mutex;

static NAMES: Mutex<Vec<String>> = Mutex::new(Vec::new());

fn intern(name: &str) -> usize {
    let mut names = NAMES.lock().unwrap();
    if let Some(i) = names.iter().position(|n| n == name) {
        return i;
    }
    names.push(name.to_string());
    names.len() - 1
}

表はプログラム全体で1つなので static に置きますが、static の値はそのままでは書き換えられません。中身を書き換えるには、共有の参照 & からでも書き換えを許す型で包みます。ここで3つの条件が重なります。1つ目に、static はどのスレッドからも同時に触れるので、型が Sync でなければ置けません。RefCell<Vec<_>> は書き換えを許しますが Sync ではないのでコンパイルエラーになり、Sync でもある Mutex を選びます。2つ目に、static の初期値はコンパイル時に計算できる式でなければならず、Mutex::new と Vec::new はどちらもそうなっている（const fn である）ので、そのまま書けます。3つ目に、表に入れる要素の型です。static の中身はプログラムの終わりまで残るので、Vec<&str> に name を入れようとすると、呼び出し側がすぐ捨てるかもしれない文字列を借りたまま残すことになり、借用の検査で拒否されます。name.to_string() で持ち主の決まった String にコピーしてから入れます。

NAMES.lock() が返すガード names を持っている間は、ほかのスレッドは表に触れません。探す処理と足す処理を同じガードの下で行うので、2つのスレッドが同時に同じ新しい名前を渡しても、両方が「無い」と判断して2回登録することはありません。探すときだけロックし、いったん離してから足すと、この保証は崩れます。入力例では "x" が 0、"y" が 1 で登録され、2回目の "x" は position が見つけた 0 を返します。番号は names.len() - 1 で、追加したばかりの要素の位置です。

掲載したのは参考実装で、唯一の正解ではありません。名前が多いなら、Mutex<Option<HashMap<String, usize>>> を None で初期化して最初の呼び出しで作るか、std::sync::LazyLock で包んだ Mutex<HashMap<String, usize>> を使うと、探す手間が名前の数に比例しなくなります。HashMap::new は const fn ではないので、static の初期値に直接は書けません。
