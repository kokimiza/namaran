rotate.zig

const std = @import("std");

const Point = struct { x: i32, y: i32 };

fn rotate(p: *Point) void {
    p.* = .{ .x = -p.y, .y = p.x };
}

pub fn main(init: std.process.Init) !void {
    var buf: [256]u8 = undefined;
    var stdout_writer = std.Io.File.stdout().writer(init.io, &buf);
    const stdout = &stdout_writer.interface;
    var p: Point = .{ .x = 1, .y = 2 };
    rotate(&p);
    try stdout.print("({d}, {d})\n", .{ p.x, p.y });
    try stdout.flush();
}

rotate は、p の指す点 (x, y) を原点の周りに反時計回りに90度回し、(-y, x) に移すつもりの関数です。main は点 (1, 2) を回して出力します。いまの出力は (-2, -2) で、本来の出力は (-2, 1) です。

Answer

Wrong

fn rotate(p: *Point) void {
    p.* = .{ .x = -p.y, .y = p.x };
}

右辺の型名を省いた構造体リテラル（anonymous struct literal）には、代入先の p.* が値を直接書き込む場所（result location）として渡され、各フィールドの式はその場所のフィールドへ直接書き込まれます。この代入は p.x = -p.y; と p.y = p.x; の2文と同じです。1文目で p.x が -2 に書き換わり、2文目はその書き換わった p.x を読むので、p.y も -2 になります。

右辺でいったん新しい構造体ができ、それが丸ごとコピーされると考えると、正しく回るはずに見えます。タプルの分割代入 p.x, p.y = .{ -p.y, p.x }; に書き換えても、タプルの各要素が p.x と p.y を書き込む場所として受け取るので、結果は同じ (-2, -2) です。

Right

fn rotate(p: *Point) void {
    const old = p.*;
    p.* = .{ .x = -old.y, .y = old.x };
}

先に p.* を old にコピーし、右辺は old だけを読みます。書き込む先の p.* と読む元の old が別の場所になるので、1つ目のフィールドへの書き込みが2つ目の式の値を変えることはなく、(1, 2) は (-2, 1) に移ります1。

  1. 言語リファレンスの Result Location Semantics の節は、配列の2要素を arr = .{ arr[1], arr[0] }; で入れ替えようとして失敗する例でこの挙動を示しています。Point{ .x = -p.y, .y = p.x } のように型名を書いた初期化は書き込む場所を受け取らないので、この形でも正しく回りますが、.{ と型名の有無だけで結果が変わる書き方は読み手に伝わりにくくなります。
